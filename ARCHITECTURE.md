# Архитектура Sonora

## Обзор

```
            ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
            │  Web (PWA)   │   │   Android    │   │    Admin     │
            │  Next.js     │   │ Compose+M3   │   │   Next.js    │
            └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
                   │  REST /v1 (OpenAPI → TS/Kotlin клиенты)│
                   ▼                  ▼                  ▼
            ┌───────────────────────────────────────────────────┐
            │ Caddy (авто-TLS, zstd/gzip, X-Request-ID)          │
            └───────────────┬───────────────────────────────────┘
                            ▼
   ┌────────────┐   ┌───────────────┐   enqueue   ┌────────────────┐
   │   recs     │◄──┤  api (FastAPI)├────────────►│  media-worker  │
   │ волна, ML  │   └──┬──┬──┬──┬───┘  Dramatiq   │ ffmpeg/Essentia│
   └─────┬──────┘      │  │  │  │                 └───────┬────────┘
         │             │  │  │  └── Meilisearch (поиск)   │
         │             │  │  └───── ClickHouse (события)  │
         │             │  └──────── Redis (кэш, лимиты, очередь, сессии волны)
         └────────────►└─────────── PostgreSQL 16 + pgvector ◄┘
                                     S3 (SeaweedFS / R2) + CDN ◄── медиа
```

## Решения и обоснования

| Развилка | Выбор | Почему |
|---|---|---|
| Админка | Отдельное Next.js-приложение `apps/admin` | Отдельный origin (можно закрыть IP-листом/SSO), тяжёлые зависимости загрузчика не попадают в бандл слушателя, независимые деплои. Общие компоненты — через пакеты. |
| Фоновые задачи | Dramatiq (Redis-брокер) | Проще Celery, надёжные ack/retry, middleware для таймаутов и приоритетов; без отдельного брокера. |
| Объектное хранилище | SeaweedFS (S3 API) локально и на VPS; R2/B2/Hetzner — сменой `SONORA_S3_*` | MinIO перестал публиковать community-образы. SeaweedFS — Apache-2.0, один процесс, подписанные URL, анонимное чтение на уровне бакета. |
| Поиск | Meilisearch | Опечатки и синонимы из коробки, мгновенный suggest, простая эксплуатация. Транслитерация — дополнительными полями при индексации. |
| Перечисления в БД | `VARCHAR + CHECK` | Добавление значения — замена ограничения в транзакции, без `ALTER TYPE`. |
| Первичные ключи | UUIDv7 | Упорядочены по времени → вставки в конец B-дерева, ID можно генерировать на клиенте (офлайн). |
| Позиции в плейлисте | Дробный индекс (строка, `COLLATE "C"`) | Перестановка трека — одна строка вместо перенумерации. |
| Ленивые связи ORM | `lazy="raise"` | Каждый запрос явно говорит, что грузит; N+1 невозможен по ошибке. |
| Ответ API | `{"error": {code, message, details, request_id}}` | Клиенты ветвятся по стабильному `code`; `request_id` связывает жалобу пользователя с логами. |
| Сжатие | На Caddy (zstd/gzip) | Не тратим CPU воркеров Python; brotli для статики — на CDN. |

## Аутентификация

* Пароли — Argon2id (64 MiB, t=3, p=4), хеширование в пуле потоков; для несуществующего
  e-mail проверяется фиктивный хеш, чтобы время ответа не раскрывало регистрацию.
* Access JWT (HS256, 15 мин): `sub`, `did` (устройство), `role`.
* Refresh — непрозрачный 256-битный токен, в БД только SHA-256. Каждая сессия устройства —
  «семейство». `/auth/refresh` блокирует строку (`FOR UPDATE`), отзывает предъявленный токен и
  выдаёт преемника.
  * Повтор только что заменённого токена (≤30 с) — гонка двух вкладок → `refresh_token_rotated`,
    клиент берёт уже обновлённую пару.
  * Повтор позже — считаем кражей: отзываем всё семейство и блокируем access-токены устройства.
* Выход/удаление устройства: строка `devices` удаляется (refresh-токены каскадно), id устройства
  попадает в Redis deny-list на время жизни access-токена — сессия обрывается мгновенно.
* Вход через Google: проверка ID-токена по JWKS Google (aud = веб- и Android-client id);
  привязка по `sub`, затем по подтверждённому e-mail.

## Каталог: видимость и кэш

Трек доступен слушателям, только если `tracks.status = 'ready'`, релиз `published` и
`publish_at` наступил (эмбарго). Это условие — в одном месте (`services/catalog.py`), его
используют все запросы; частичные индексы `WHERE status = 'ready'` делают его дешёвым.

Ответы каталога несут strong ETag (BLAKE2b тела) и `Cache-Control`: `public` для гостей
(можно кэшировать на CDN), `private` для авторизованных (поле `playable` зависит от фильтра
explicit), `Vary: Authorization`.

Пагинация — keyset-курсоры (непрозрачный base64 JSON с ключом сортировки последней строки).

## Ограничение частоты

GCRA в Redis одним Lua-скриптом: гладкое ограничение без всплесков на границе окна, один
round-trip. Общий бюджет на пользователя (или IP для гостей) для всех `/v1`; строгий per-IP
бюджет для эндпоинтов с паролями. `/auth/refresh` — только общий (CGNAT у мобильных операторов).

## Данные

* PostgreSQL — источник истины (34 таблицы, `services/api/src/sonora_api/models`).
  Эмбеддинги: `content_vec` 512 (аудио-модель), `collab_vec` 128 (матричная факторизация),
  `hybrid_vec` 256 (слияние) — HNSW, косинусное расстояние. Смена размерности = миграция +
  переэмбеддинг.
* ClickHouse — события прослушивания (`infra/clickhouse/001_events.sql`):
  `ReplacingMergeTree` с дедупликацией по `event_id`, партиции по месяцу,
  `ORDER BY (user_id, ts)`; материализованные представления: прослушивания трека за день
  (засчитывается ≥30 с или ≥50 %), уникальные слушатели артиста за день (месячные = `uniqMerge`
  за 28 дней), доля дослушиваний.
* Redis — rate limit, deny-list устройств; далее — очереди Dramatiq, сессионные векторы волны.

## Загрузка и обработка аудио

```
admin/CLI ── POST /v1/admin/uploads ──► API: upload_jobs (pending_upload) + presigned PUT
    │                                        │
    └── PUT файл ──► S3 sonora-uploads       │
    └── POST /complete ──► API проверяет размер в S3 → queued → Dramatiq (Redis) ──► media-worker
                                                                                      │
   probe → authenticity → tags → fingerprint → loudness → catalog → transcode → waveform
         → artwork → preview → lyrics → publish            (чекпоинт каждого этапа в upload_jobs.state)
```

* **Целостность.** ffmpeg молча пересинхронизируется на битых фреймах, поэтому для FLAC
  декодированный PCM сверяется с MD5 из STREAMINFO; для MP3 — предупреждения декодера.
* **Поддельный lossless.** Ищется «обрыв» спектра (>25 дБ на 1 кГц) выше 10 кГц — след
  low-pass фильтра MP3/AAC-кодера. Только предупреждение.
* **Дубликаты.** SHA-256 (точная копия) и Chromaprint: сходство ≥0.95 при длительности ±3 с.
  Замерено: та же запись в MP3 128/AAC 96 даёт ≥0.999, разная музыка ≈0.6. Отпечатки с малым
  числом различных значений (дроны, тоны, тишина) не используются для блокировки.
* **Лесенка качеств** никогда не апскейлит (таблица в `media-worker/ladder.py`). Hi-Res —
  только 24 бит и ≥48 кГц. MP3-источник: «высокое» — исходные байты без перекодирования.
* **HLS.** Каждое качество — цельный файл (офлайн) + fMP4-сегменты по 6 с из него же (stream
  copy). `master.m3u8` для «Авто» содержит только lossy-варианты (normal первым — быстрый
  старт); Lossless/Hi-Res — явный выбор, отдельные плейлисты.
* **Gapless.** ffmpeg при упаковке fMP4 обнуляет edit list; воркер переписывает `elst` в
  `init.mp4`: priming (1024 сэмпла AAC) и реальная длительность. Задержка/padding каждого
  файла хранятся в `track_files` для клиентов, которым нужна ручная обрезка.
* **Громкость.** EBU R128 → track gain к −14 LUFS с ограничением по true peak (−1 dBTP);
  album gain — энергетическое среднее треков альбома, ограниченное самым громким пиком.
* **Ключи объектов** содержат id задачи или хеш содержимого → объекты неизменяемы,
  `Cache-Control: immutable` на год. `sonora-media` — приватный (подписанные URL),
  `sonora-public` — обложки, анонимное чтение.
* **Ошибки.** Проблемы файла (`MediaError`) показываются админу как есть; сбой окружения
  (нет ffmpeg и т.п.) — «Internal error», и воркер с отсутствующим ffmpeg не стартует вовсе.

## Стриминг

```
плеер ── GET /v1/tracks/{id}/stream?quality=auto ──► API: проверка доступа, explicit-фильтр,
                                                       выбор качества → /v1/stream/<token>/master.m3u8
плеер ── GET /v1/stream/<token>/normal/playlist.m3u8 ──► API отдаёт текст плейлиста из S3
плеер ── GET /v1/stream/<token>/normal/seg_00003.m4s ──► 302 → подписанный URL S3 на 5 минут
```

* Токен потока (JWT, отдельный ключ — не годится как access-токен) несёт префикс HLS трека,
  поэтому запрос сегмента не ходит в БД. Живёт ≥ 1 ч (3× длительность трека, ≤ 12 ч).
* Плейлисты отдаёт API, поэтому относительные URI сегментов указывают обратно на API, и каждый
  сегмент получает свежую подпись — истечение подписей посреди трека невозможно.
* Путь проверяется по allow-list (`master.m3u8`, `<quality>/(playlist.m3u8|init.mp4|seg_NNNNN.m4s)`).
* «Авто» = ABR по lossy-вариантам; явное качество ограничивается доступным сверху вниз
  (Hi-Res на CD-релизе → Lossless). Ответ включает track/album gain для нормализации.

## Веб-клиент

* Один origin: Caddy маршрутизирует `/v1/*` → API, `/sonora-*` → S3, остальное → Next.js.
* Сессия: refresh-токен в httpOnly-cookie (`/api/session/*` — серверные роуты Next), access-токен
  только в памяти; при `token_expired` клиент API один раз обновляет токен и повторяет запрос.
* Плеер: единственный `<audio>` в корневом layout (не прерывается при навигации), явная
  машина состояний, очередь с shuffle/repeat, нормализация через Web Audio (кроме нативного HLS
  в Safari, где WebKit глушит звук), Media Session, горячие клавиши, предзагрузка ссылки на
  следующий трек за 20 с до конца, восстановление очереди и позиции после перезагрузки.

## Управление сайтом

* Админ-API под `/v1/admin/*` (роль `admin`), списки с offset-пагинацией (`total` для таблиц);
  публичные списки остаются на keyset-курсорах.
* **Главная** — упорядоченные блоки `home_sections` (`hero`, `releases`, `tracks`, `playlists`,
  `artists`, `genres`) с конфигом: источник (`new`/`popular`/`hires`/`recent`/`all`/`manual`), вид,
  лимит, ручные id, картинка и ссылка баннера. `/v1/home` собирает блоки для конкретного слушателя
  (`recent` — у каждого своё), пустые блоки скрывает. Пока блоков нет, отдаётся встроенный шаблон;
  «Собрать из шаблона» превращает его в редактируемые блоки. Предпросмотр — тот же резолвер без записи.
* **Картинки** (обложки плейлистов, жанров, релизов, фото артистов, баннеры 16:7) — один
  эндпоинт загрузки: рендишены AVIF/WebP/JPEG, blurhash и палитра считаются тем же кодом, что в
  media-worker (`sonora_api.media.*` — общий модуль для API и воркера).
* **Рубильники сервиса** — `platform_settings` (JSON) → `PlatformConfig`; применяются сразу:
  регистрация, доступные качества (стрим ограничивается сверху), превью для гостей,
  объявление и режим обслуживания (публичный `/v1/platform`).
* **Блокировка** — `users.blocked_at`; refresh-токены отзываются, а проверка на каждом запросе
  отсекает уже выданные access-токены.
* **Прослушивания** — `/v1/events/batch` (идемпотентно по `event_id`); засчитывается после 30 с или
  половины трека. «Сейчас слушают» — короткоживущие ключи `now:{user}` в Redis.

## Визуальная система

* Liquid glass: панели `.liquid` (blur + насыщенность + блик сверху), свечение края под курсором
  (`SpotlightZone` пишет координаты в CSS-переменные — без ре-рендеров React).
* Живой фон: три «облака» на анимируемых `@property`-цветах. Цвета берутся из палитры обложки
  играющего трека; `requestAnimationFrame` читает `AnalyserNode` и пишет `--energy`/`--beat`, от
  которых фон дышит и пульсирует в такт. При `prefers-reduced-motion` анимации выключены.

## Наблюдаемость

Структурированные логи (structlog, JSON в проде): строка доступа на каждый запрос с шаблоном
маршрута (`/v1/tracks/{track_id}` — низкая кардинальность для метрик), статусом и длительностью;
`request_id` в каждой записи и в заголовке ответа. `/healthz` (liveness), `/readyz` (Postgres + Redis).
