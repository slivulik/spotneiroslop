### Important

**I-1 [important] The endless wave stalls once the catalogue is exhausted: server and client each run their own "no repeats" policy and they contradict each other** (root cause of the failing e2e `discovery-flow` «wave keeps going past the catalogue size»).
- Where: `services/api/src/sonora_api/services/wave.py:72` (`REPEAT_WINDOWS = (30, 10, 1, 0)`), `:486-491`; `apps/web/src/lib/recommend.ts:132-135` (`freshTracks(playable, now.queue.items.slice(-30)…)`), `:144` (15 s back-off); `apps/web/src/lib/wave.ts:139-146`.
- What happens: when nothing unserved is left, the server excludes the last 30 served ids, then the last 10, then 1. With N tracks in the catalogue and 10 < N ≤ 30 it therefore answers with only `N − 10` tracks per call. The web client then throws those away, because every one of them is among the last 30 items of its queue, adds nothing while at least one upcoming track exists, and backs off for 15 s. The queue only grows again when the listener is already on the last track and the back-off has expired. Meanwhile the server has already recorded the discarded tracks in `served`, so the server's memory drifts from what the listener actually got.
- Evidence (probe, 12-track seed): `batch sizes (start limit 20, then next limit 10): [12, 2, 2, 2, 2, 2, 2, 2, 2]`. e2e: 12 «Следующий» clicks in ~8 s, queue stays at 12.
- Should: one authority. The server already knows what it served; the client must not second-guess it.
- Fix: (1) client — dedupe a refill only against the current track and the *upcoming* part of the queue, never against played history; drop the "last 30" rule and its fallback branch. (2) server — in the exhausted path return a full `limit` batch ordered least-recently-served, with the window computed as `max(1, playable_count − limit)` instead of fixed steps; do it in one query instead of re-running `_candidates` up to four times. (3) add an API test "limit 10 against a 12-track catalogue returns 10 after exhaustion, never the last served" and a `wave.test.ts` case for the refill filter.

**I-2 [important] Starting a radio wipes the listener's saved «Моя волна» tuning**
- Where: `services/api/src/sonora_api/services/wave.py:253-261` (`latest_settings` takes the newest session of *any* seed type); `apps/web/src/lib/recommend.ts:79` (radios always start with `ANY_WAVE`), `:191-196` (`loadWaveSettings` adopts the server copy); `apps/web/src/components/SettingsSync.tsx:57` (called on every sign-in / app load).
- What happens: tune the wave (calm + discover) → start a radio from any track → reload. `GET /v1/me/wave/settings` now returns all nulls, `wavePending` is false, so the local tuning is overwritten with «любое».
- Evidence (probe): `settings after tuned start: {'character': 'discover', 'mood': 'calm', 'language': None}` → `settings after radio start: {'character': None, 'mood': None, 'language': None}`.
- Should: the tuning is a user preference, not a by-product of session history.
- Fix: minimal — `latest_settings` filters `WaveSession.seed_type == "user"` and gets a test with an interleaved radio. Proper — store the tuning in the existing user-settings document (`/v1/me/settings`, already synced by `SettingsSync` with `syncPending`), and let a session only snapshot it; this removes `wavePending`, `settle()` and the second sync channel in `lib/recommend.ts:48-52,189-199`.

**I-3 [important] Two parallel ranking pipelines, glued together through private names**
- Where: `services/api/src/sonora_api/services/wave.py:64` and every `rec._…` use (`_now`, `_blend`, `_seed_taste`, `_co_listened`, `_candidate_ids`, `_load`, `_score`, `_diversify`, `_top`, `_norm`, `_Cand` — 11 private members, ~30 call sites, e.g. `:470-506`, `:524`, `:665`); `services/api/src/sonora_api/services/recommend.py:331-353` (old `wave()`); `recommend.py:149` (`catalog._tracks_query`).
- What happens: `recommend.wave()` (stateless `GET /v1/me/wave`) and `wave._pick()` (sessions) both spell out taste → blend → co-listening → candidates → load → hide dislikes → score → diversify, with differences that are already drifting: the session path filters `catalog.is_playable` and widens the pool, the old path does neither; the old path excludes via `_score(..., exclude)`, the new one passes a dummy `set()` (`wave.py:500`). Any round-2 change to scoring (DSP features, embeddings, bandit) has to be made twice and `wave.py` breaks silently on any refactor of `recommend.py` internals.
- Who still uses the old route: Android only, as a fallback (`apps/android/app/src/main/java/com/sonora/app/data/repo/Wave.kt:152`); the web client no longer calls it.
- Fix: extract a `services/recs/` package with a public surface — `taste.py` (`Taste`, `taste()`, `seed_taste()`, `blend()`), `candidates.py` (`Candidate`, `load()`, pool sources), `scoring.py` (`score()`, `diversify()`), `blocked.py`. `services/wave.py` and the mixes import only public names. Make `GET /v1/me/wave` a thin adapter over the same `pick()` (served = `exclude`, no tuning) and mark it `deprecated=True` in OpenAPI until Android drops the fallback.

**I-4 [important] `wave_sessions` grows without bound; nothing ever deletes or reuses a session**
- Where: `services/api/src/sonora_api/services/wave.py:185-195` (insert on every start); no `delete(WaveSession)` anywhere in `services/`; clients: `apps/web/src/lib/recommend.ts:63` (every «Моя волна» press), `:79` (every radio), `:122` (every expired-session recovery), `:160` (every retune, debounced only by 450 ms; a retune that loses the `retuneSeq` race at `:162` leaves an orphan session).
- What happens: one row + JSONB per play press, forever. The Redis state expires after 12 h, the row does not. `last_event_at` is written only by feedback (`wave.py:248`) and read by nobody; `next_batch` does not touch it; the only index, `ix_wave_sessions_user_recent (user_id, last_event_at DESC)` (`models/platform.py:14`), does not match the only query that reads the table by user (`ORDER BY started_at DESC, id DESC`, `wave.py:258`).
- Fix: a periodic purge in the worker (delete sessions with `last_event_at < now() − 30 days`), `next_batch` bumps `last_event_at`, `latest_settings` orders by the indexed column (or is replaced per I-2), and the client reuses the live session when the tuning did not change instead of opening a new one per press.

**I-5 [important] Every `next` runs the whole pipeline with full-catalogue scans, inside the session lock**
- Where: `wave.py:527-536` and `:574-582` (`ORDER BY random() LIMIT 300` over all visible tracks, with `Track.id NOT IN (<up to 2000 served ids + candidates>)`); `:586-590` + `:593-658` (unanchored `ILIKE '%word%'` over genre/mood names — ~30 OR-ed patterns per mood — and `regexp_match` over every track title and artist name); `:738` (`cast(lyrics.body AS text) ~ '[Ѐ-ӿ]'` — a regex over the full lyrics JSON of every candidate, per request); `:486-491` (`_candidates`, i.e. 3 + 1 + 3 queries, repeated up to five times once the catalogue is exhausted).
- What happens: by reading, one batch is roughly 20 queries on the happy path and 40+ when the wave wraps, none of them cached between calls of the same session, all while `_exclusive` holds the session lock and a pooled connection. Fine for 12 tracks; with the larger seed and round-2 imports (thousands of tracks) this is the slowest endpoint in the API and it is called by the queue-low handler on playback progress ticks.
- Not measured: I counted queries by reading, not with a statement counter (see "Not checked").
- Fix: (1) precompute per-track signals once — `tracks.language` (ru/foreign/instrumental/unknown) and a mood vector — in the worker's enrich/analyse stage, so `next` filters on indexed columns instead of regex/ILIKE; (2) cache the session's taste, co-listening counter and candidate pool in Redis next to `served` (same 12 h TTL) and recompute only on feedback; (3) replace `ORDER BY random()` with `TABLESAMPLE`/random-offset on the id index; (4) do the wrap-around in one pass (see I-1).

**I-6 [important] Hand-rolled Redis lock: expires mid-work, releases non-atomically, falls through silently; no concurrency test**
- Where: `wave.py:77-81`, `:349-366`, used at `:322-328`.
- What happens: (a) the lock TTL is 10 s with no renewal while the holder runs the 20–40 queries of I-5 — on a slow database the lock expires and a second `next` runs concurrently, which is exactly the duplicate-batch race the lock exists to prevent; (b) a waiter polls 50 × 0.1 s = up to 5 s while already holding a DB connection with an open transaction (`_own` has run; in `start` the INSERT is flushed, `:193`); (c) after 5 s it proceeds without the lock and without a log line or metric; (d) release is `GET` then `DELETE` (`:364-366`), so a holder whose lock expired can delete the next holder's lock. The stated behaviour "two `next` calls racing each other cannot both hand out the same tracks" has no test.
- Fix: use `redis.lock(key, timeout=…, blocking_timeout=…)` from redis-py (Lua compare-and-delete, optional extend), or better drop the lock: compute the batch, then claim it atomically with one Lua script that appends only ids not already in `served` and returns what was claimed; retry once if it came back short. Log at warning when the lock/claim degrades. Add a test that fires two `next` calls with `asyncio.gather` and asserts disjoint batches.

**I-7 [important] A batch is not topped up from relaxed filters, so strict settings produce 1-track batches and a request per track**
- Where: `wave.py:502-506` — the first relaxation level with *any* fitting track returns only those.
- What happens: with mood/language/character set and few matching tracks left, `next?limit=10` answers with one or two tracks. The client's queue-low handler (`apps/web/src/player/controller.ts:119`, fires while fewer than 3 are upcoming) then calls `next` again immediately, and again — each call the full pipeline of I-5. `tests/test_wave.py::test_mood_from_genre_names` pins this behaviour (`first` has 3 of 10, the next batch is exactly `[loud]`).
- Fix: fill to `limit` level by level — take everything that passes level 0 in score order, then append from level 1, 2, 3 until the batch is full; keep the order so strict matches play first.

**I-8 [important] «Не нравится» leaves the like in place; a track can be liked and disliked at once**
- Where: `wave.py:215-232` — `liked` deletes the dislike, `disliked` does not delete the like.
- What happens: the disliked track stays in «Любимые треки» and, worse for recommendations, `recommend.taste()` (`recommend.py:75-76`) keeps giving it weight 3, which boosts its artist and genres in every later wave and mix.
- Evidence (probe): `liked 204`, `disliked 204`, `still in liked tracks after dislike: True`.
- Fix: in the `disliked` branch also `delete(LikeTrack)` for that user/track in the same transaction; add the mirror of the existing "liking lifts the dislike" assertion to `test_dislikes_never_play_in_any_wave`.

**I-9 [important] `GET /v1/tracks/{id}/lyrics` now blocks on two sequential third-party HTTP calls inside the request**
- Where: `services/api/src/sonora_api/routers/public.py:87-88`; `services/api/src/sonora_api/services/lyrics_on_demand.py:118-119`, `:148-152` (`asyncio.to_thread(lrclib.find, …)`); `services/api/src/sonora_api/enrich/lrclib.py:46-73` (`/get`, then `/search`, each with `httpx.Timeout(8.0, connect=5.0)`, `enrich/common.py:11`).
- What happens: the first listener to open a track without lyrics waits for LRCLIB — up to ~16 s of read time (more with connects) — with a spinner in the lyrics panel, and the lookup occupies a thread of the default executor for that long. On the 4-core box that executor has 8 threads and is shared with the other `to_thread` users of the API; a listener skipping through the wave with the lyrics panel open starts one lookup per track. The lock (`LOOKUP_LOCK_TTL = 30 s`, `:37`) is released with a bare `DELETE` (`:119`), so a lookup that outlives the TTL deletes the next holder's lock.
- Should: a read endpoint answers from the database; slow third-party work belongs to the worker, as it already does for uploads and the backfill.
- Fix: on a miss, enqueue a `lookup_lyrics(track_id)` Dramatiq task (dedupe with the same Redis `SETNX`) and answer 204 with `Retry-After: 5`; the client refetches once. If the synchronous path stays for this round, give the whole lookup a hard `asyncio.wait_for(…, 3.0)` budget and a dedicated bounded executor, and release the lock with a token check.

**I-10 [important] An admin's «remove these lyrics for good» lives only in Redis**
- Where: `services/api/src/sonora_api/routers/admin_catalog.py:98-101` (`remember_miss(ctx.redis, track_id, ttl=None)`); read at `lyrics_on_demand.py:109`.
- What happens: the tombstone that stops wrong automatic lyrics from coming back is a Redis key without TTL. Redis is the cache / rate-limit / queue store here (the dev stack runs it with `--save "" --appendonly no`, `tools/dev/stack.sh:76`); a restart, `FLUSHDB`, an eviction policy or a move to another instance silently undoes every such moderation decision, and the same wrong lyrics are fetched again on the next play. Nothing in the admin UI shows or lifts the block either.
- Should: a moderation decision is durable catalogue state.
- Fix: a nullable `tracks.lyrics_lookup_blocked_at` (or a `Lyrics` row with `source = 'removed'`) written in the same transaction as the delete; `find_missing` checks the column; Redis keeps only the 7-day "LRCLIB had nothing" cache. Add the test "deleted by admin → still not fetched after `redis.flushdb()`".

**I-11 [important] `tools/dev/stack.sh env N` promises per-slot test databases that do not exist**
- Where: `tools/dev/stack.sh:12` (usage: "print `export …` lines (also the per-slot TEST databases)"), `:58-62` (exports), `:112-117` (`ensure_db` creates them — but it is only called from `api_up`, `:121`); `docs/team/AGENT-GUIDE.md` tells every agent to `eval "$(tools/dev/stack.sh env N)"` and run pytest.
- What happens: on a slot whose API was never started, the documented sequence fails on the first test.
- Evidence: `eval "$(tools/dev/stack.sh env 4)" && cd services/api && uv run pytest -q -x` → `sqlalchemy.exc.DBAPIError: … database "sonora_test_4" does not exist`. After creating the two databases by hand: `130 passed in 56.43s`.
- Fix: add a `test-db <slot>` command (or make `env` call the test-database half of `ensure_db` on stderr-silent best effort) and name it in AGENT-GUIDE; the worker test database has the same gap.

### Minor

**M-1 [minor] `feedback()` commits twice and nudges outside the transaction** — `wave.py:220` calls `library.set_saved`, which commits internally (`services/library.py:101`), so the dislike deletion and the like are committed before the artist/genre lookup and the `last_event_at` update (`:248-249`); Redis nudges follow at `:250`. A failure between the steps leaves a like without its session effect, and a client retry double-applies `hincrbyfloat` (nudges are not idempotent). Fix: give `library` a non-committing `save()` used by both callers; make feedback idempotent per `(session, track, action)` with a short-lived Redis `SETNX` guard.

**M-2 [minor] Feedback accepts any track id** — `wave.py:212` checks only that the row exists (not visibility, not that this session ever served it), so a client can nudge artists/genres with tracks the wave never played. Fix: require membership in the session's `served` list (or the seed track) and answer 404 otherwise.

**M-3 [minor] `started` feedback is a write that nothing reads** — `apps/web/src/lib/recommend.ts:221-223` posts `started` for every track; server side it only sets `last_event_at` (`wave.py:234-249`), which no code reads (I-4). One SELECT + UPDATE + COMMIT per track start for no effect. Fix: either use it (bump session liveness for the purge, feed the "served but never started" signal) or stop sending it.

**M-4 [minor] `seed_artist` is smuggled into the `settings` JSONB** — `wave.py:98`, `:181-183`, `:312`; typed as `dict[str, Any]` (`:181`, `:294`; `models/platform.py:21`). No client sends both seeds. Fix: reject "both seeds" with a model validator on `WaveStartIn` (422), delete `_SEED_ARTIST`, and type the column as a `TypedDict`/validated `WaveSettings`.

**M-5 [minor] Unseeded RNG in the ranking** — `wave.py:497` and `recommend.py:352` create `random.Random()` inline. The offline evaluation being built in parallel cannot reproduce a ranking. Fix: take the `Random` (or a seed) as a parameter of the pick function; production passes a fresh one.

**M-6 [minor] `lib/recommend.ts` is now the wave session client and registers player handlers as an import side effect** — `apps/web/src/lib/recommend.ts:262-266`; the player exposes single-slot setters (`controller.ts:337-343`), so a second consumer (round 2 «Мэтч» needs the same started/finished/left events) would silently replace the wave's handler. Module state `refilling` / `refillAfter` / `retuneTimer` / `dislikedId` (`:100-101`, `:153-154`, `:215`) is not reset on sign-out. Fix: move the session client to `lib/wave-session.ts`, leave queries in `recommend.ts`; turn `setTrackEventHandler` into `player.on("track", fn)` returning an unsubscribe; register from one explicit bootstrap.

**M-7 [minor] Every failure in the wave client is swallowed** — `recommend.ts:67-69`, `:92-94`, `:140-142`, `:169-171`, `:196-198`, `:209`: bare `catch {}`. `playWave()` returns `false` for offline, 5xx, 401 and "empty catalogue" alike, so the UI cannot say why nothing started, and lost feedback (a skip sent while offline) is never retried. Fix: return a discriminated result (`{ ok: false, reason }`), surface it in the hero, and queue feedback through the existing events batch path instead of fire-and-forget POSTs.

**M-8 [minor] `lyrics_on_demand` works around its own dependency instead of fixing it** — `lyrics_on_demand.py:54-76` wraps the HTTP transport (`_Watched`) only to learn whether `lrclib.find` failed, because `find` swallows every error and returns `None` (`enrich/lrclib.py:72-73`); `:79-86` then re-implements proxy detection with `urllib.request.getproxies()` because passing a transport switches httpx's own env-proxy handling off. Fix: make `lrclib.find` return a tri-state (`Found | NotFound | Unavailable`) or raise `LrclibUnavailable`; both callers (worker enrich, on-demand) branch on it and the transport wrapper and proxy code go away.

**M-9 [minor] The import use case is written in the router** — `services/api/src/sonora_api/routers/admin_sources.py:80-105`: id clean-up, re-resolve, missing/busy checks, job creation, commit and enqueue all sit in the route function; `:17` imports the private `_job_out` from another router (`routers/admin.py`). Every other feature of the round keeps routes thin. Fix: `importer.queue_import(session, broker, source, admin, ids, publish) -> list[UploadJob]`; move `_job_out` to `schemas/admin.py` as `UploadJobOut.from_job`.

**M-10 [minor] Import is check-then-insert, and enqueue happens after the commit with no recovery** — `admin_sources.py:93-103`. Two admins (or a double click) pass the `busy` check together and queue two jobs for one recording; the second only fails after downloading the whole file, in the worker (`pipeline.py` `stage_fetch`/`stage_catalog` → "уже есть в каталоге"), or — if both reach `stage_catalog` together — on the unique index as a raw `IntegrityError` rather than a `MediaError`. If the process dies between `session.commit()` (`:101`) and the last `enqueue_process_upload` (`:103`), the job stays `queued` forever. `importing_ids` (`services/sources/importer.py:35-45`) loads the options of every active import job to compare ids in Python. Fix: a partial unique index on `upload_jobs ((options->>'source'), (options->>'external_id')) WHERE status IN ('pending_upload','queued','running')` and `ON CONFLICT DO NOTHING`; a sweeper (or transactional outbox) that re-enqueues `queued` jobs older than a minute; catch `IntegrityError` in `stage_catalog` and turn it into the same `MediaError`.

**M-11 [minor] `ImportJobOptions` is re-validated in four stages** — `imports.spec(ctx.options)` at `services/media-worker/src/sonora_media/pipeline.py` `stage_fetch`, `stage_tags`, `stage_catalog`, `_catalogue_cover`. Fix: one cached `JobContext.import_job` property. Related: the API↔worker contract model lives in `sonora_api/services/sources/base.py:113-169` next to HTTP client code, and `services/catalog.py:32` imports `SOURCE_TITLES` from the sources package (catalogue → importer dependency). Move the contract and the titles to a dependency-free module (`sonora_api/contracts/imports.py`).

**M-12 [minor] No licence policy switch** — `services/sources/licenses.py:41-56` accepts every CC variant, including NC and ND; nothing in `Settings` (`core/config.py:63-67`) lets the owner exclude them, although the service transcodes (derivative question for ND) and may one day carry ads/subscriptions (NC). This is a product/legal decision, flagged here because the code gives it no place to live. Fix: `SONORA_SOURCES_ALLOWED_LICENSES` (default: all free ones) applied in `parse_license` callers, and the licence class shown in the admin search results.

**M-13 [minor] Migration 0007 — safe, with three loose ends** — `services/api/migrations/versions/0007_track_licence.py`. Up: six nullable `ADD COLUMN` (metadata-only) and a partial unique index — fine at today's size, but the index is built non-concurrently inside the migration transaction, i.e. `tracks` is locked for writes for the duration; adopt `CREATE INDEX CONCURRENTLY` in an autocommit block as the house rule before the catalogue grows. (1) `:35` the uniqueness is on `(source_name, source_external_id) WHERE source_external_id IS NOT NULL`, but nothing forces `source_name` to be set — a NULL `source_name` defeats it; add `CHECK ((source_name IS NULL) = (source_external_id IS NULL))` and `CHECK (source_name IS NULL OR license_code IS NOT NULL)`. (2) `source_name` is a free `String(32)` (`models/catalog.py:175`) while ARCHITECTURE.md prescribes `VARCHAR + CHECK` for enumerations (`str_enum`). (3) Down drops the licence and attribution columns — the data a CC BY import legally depends on — without a guard; refuse to downgrade while `license_code IS NOT NULL` rows exist, or say so in the docstring. The up/down/up cycle itself is exercised by `tests/conftest.py:71-77` and passes.

**M-14 [minor] `tools/dev/stack.sh` robustness** — (a) `:35` `mkdir -p "$RUN"` runs for every command, so `env 4` or a bare `status` creates a slot directory and `status` then lists a slot that was never started; (b) `:21` `((SLOT <= 60))` treats `08`/`09` as invalid octal and aborts with a bash arithmetic error instead of the usage message — use `((10#$SLOT <= 60))`; (c) `:98-104` `stop_one` kills whatever process group now owns the PID in the pid file (after a reboot or PID wrap that is someone else's process) — check `/proc/$pid/cmdline` or store the start time; (d) `:163-166` `reset` drops the database but leaves the slot's Redis databases (queue with jobs for rows that no longer exist, `lyrics:miss:*`, wave state, rate limits) — `redis-cli -n … flushdb` for the slot's three indexes; (e) `:167-172` `snapshot` drops `sonora_seed` *before* it knows the copy will succeed — create `sonora_seed_new`, then swap; (f) `:131-144` every slot started from the same checkout shares one `apps/web/.next`, so `web N` rebuilds the static chunks under another running slot (the review team runs slots 0–3 from the lead's checkout); (g) `:88-91`, `:150` images `chrislusf/seaweedfs:latest` and `caddy:2.10-alpine` are unpinned/half-pinned; (h) no lock against two concurrent `up` of the same slot; `status` does not show the edge container.

**M-15 [minor] `tools/dev/worktree.sh` robustness** — (a) `:13`, `:27` missing arguments die with "unbound variable" under `set -u` instead of printing the usage; (b) `:21-24` a failed `pnpm install` / `uv sync` prints a line to stderr but the script still exits 0 and prints the worktree path as if it were ready, and both tools' own error output is discarded (`2>/dev/null`), so the reason is lost; (c) `:28` `worktree remove --force` deletes uncommitted work without a word — given that agents can be cut off mid-task by the usage limit, refuse when `git status --porcelain` is non-empty unless `--force` is passed explicitly.
